## 核心洞察（讨论外产出，待汇总）

### I1 · 缓存与模型自主「不冲突」的根因：作用在不同抽象层
- 缓存是**字节前缀**概念；模型自主是**语义决策**概念。二者解耦的关键是**三层消息模型**：
  - **S 层（稳定前缀）**：system 骨架 + 工具 schema + 早期历史（append-only）→ 进缓存
  - **W 层（工作记忆）**：模型提炼的最新状态 / tool_result 加工产物 / 动态指令 → 放 messages 末尾
  - **P 层（参数）**：temperature / reasoning_effort / thinking → API 独立字段，**根本不在 messages 里**
- 推论：**模型自主调参（P 层）零缓存影响**——这是被普遍忽略的一点。缓存的是 messages，参数是 API 字段。

### I2 · 「加工 context」≠「改写历史」
- 误解澄清：加工 tool_result 是「模型读取后产生新的提炼层」，**不是替换原始结果**。
- 原始 tool_result 进入 S 层（稳定历史），提炼产物进入 W 层（工作记忆）。两者并存，缓存不破。
- 约束纪律：**模型自主加工时只能「追加」，不能「改写前缀」**——这是「既要又要」的唯一硬约束。

### I3 · multiagent 通信 = 「协议稳定 + 载荷动态」双层（硬件启发）
- 类比 CPU/cache：通信协议（消息类型/字段/寻址）像 **ISA 指令集**，固定、紧凑、listener 可解析；载荷编码像 **微指令/寄存器值**，由模型自定义最精简内部表示（甚至加密语言）。
- 所以「模型自定义加密语言」不破坏 listener 理解——**协议骨架是代码级固定的，只有载荷是模型生成的**。
- 与缓存同理：协议骨架进缓存前缀（稳定），载荷放末尾（动态）。

### I4 · 工作流插槽 = session 图的「代码化」
- 用户说的「代码中的内容是传输进来的」：LLM 生成工作流代码放到运行插槽执行，从代码层强制工作流，而非自然语言逐步指令。
- 与 session 图天然契合：工作流 = nodes（步骤）+ links（转移/依赖），就是「可执行的 session 图」。
- 本质：**agent 自我编程**——LLM 生成自己的确定性子程序，agent loop 从「LLM 逐步推理」变成「解释执行工作流代码」。

### I5 · 参数自主（P 层）是「零成本」的模型自定义切入点
- 因为参数不在缓存范围，L2 的「模型自主调参」是**风险最低、收益最早**的落地项——不需要动缓存策略即可实现。

### Q1 · W 层（工作记忆）的规模与失效策略
- 模型提炼的工作记忆增长到多大？是否也需要「压缩/滑窗」？W 层压缩会不会反而影响 S 层缓存（若 W 层内容被回填进 S 层）？

### Q2 · 「协议骨架」的具体形态
- multiagent 通信协议是否复用 session 的 nodes/links？还是独立的「消息总线」+「结构化信封」？
- 载荷编码（模型自定义加密语言）是否需要「解码约定」共享给 listener？还是 listener 用自身 context 吸收，不显式解码？

### Q3 · 工作流插槽的「受控程度」
- 插槽执行的代码有多大的能力面（能否调用工具/其他 agent/改 session）？安全边界在哪（全信任模型下仍要防死循环/资源耗尽）？

### Q4 · Pi 式「中途补充」的扩展点形态
- 用户中途插话如何进入 agent loop？作为「高优先级事件」打断当前步骤？还是排队到下一步？中断 vs 排队对缓存前缀的影响？

### Q5 · L3 的「思维链压缩」与「直接喂结论」的取舍
- 用户说「直接喂思维链 token 消耗不起」——但完全只喂结论可能丢失关键推理上下文。是否要「结构化中间状态」（关键决策点 + 状态摘要）而非完整思维链？

## 追加：Q2/Q3 拍板 + CPU 抽象落地（2026-08-13 第二轮）

### 用户拍板
- **Q2（协议骨架形态）**：独立于 session。session 的 link 是帮用户管理文件（知识体系），不是 multiagent 通信。协议骨架要支持：**时序精确把控、优先级排序、使用时间预估**——保证功能不因软件结构受制约。
- **Q3（插槽受控程度）**：代码插槽要**很受限**（AI 会幻觉，权限大整个软件受影响）。核心原则：**「代码强度不能被实施」**——模型能描述的能力，受限于解释器的白名单操作集。自主编写 skill/memory/mcp 工具、自定义工作流都是简单操作。
- **明确**：multiagent 通信**不是 session 图**，不需要实例化方法；复用 node+link 只是设计理念层面，代码实践就是 append/+ 号。

### CPU/cache 三步法提炼的逻辑抽象（供具体化）
1. **分层传输**：不同「通信距离/频率」的数据走不同通道（机柜间 IB / 核内寄存器）→ 消息分「通道」。
2. **DMA 不经主控**：数据搬运不经过中心 CPU 中转 → 消息池不是「manager 存、expert 取」，而是共享数据区直读（黑板）。
3. **局部性原理**：时间局部性 + 空间局部性 → 高频小数据共享（进池）、低频大数据私密（1v1）。**消息池省内存的原理**。
4. **缓存行固定粒度**：64 字节为单位 → 通信以「固定结构信封」为单位，不是逐 token。
5. **缓存一致性 MESI**：多核共享数据要有失效/更新协议 → 消息池全局信息改动要广播失效通知（events）。
6. **ISA 固定契约**：指令编码固定、编译器/硬件都遵守 → 协议信封固定、载荷自由（呼应 design-ideas #11 无为而治）。
7. **寄存器重命名**：消除假依赖、独立运算并行 → 消息用「依赖声明」而非「到达顺序」定义时序。
8. **流水线**：分段并行 → agent 间流式传递（边产出边传）。

### 新增洞察
- **I6 · 消息池省内存的原理 = 共享 L3 cache**：全局信息只存一份，多 agent 共享，而非每 agent 各存副本。省的是「重复存储」；但只有「高频共享」进池（局部性），低频私有走 1v1，否则池膨胀反违背局部性。
- **I7 · 协议骨架 = ISA，字段固定**：信封 `{ from, to, type, priority, deadline, seq, deps, payload }`——priority=优先级、deadline=时间预估、seq+deps=时序（依赖声明而非到达顺序）、payload=内容自由。这直接满足 Q2 的三项要求。
- **I8 · 代码插槽安全 = 「受限 DSL + 白名单解释器」**：模型生成「声明式工作流数据」（节点+转移+条件），固定的解释器只执行白名单操作（调工具/读写 session/发消息/条件/带上限循环）。类比 SQL——任意查询可写，但能力面=解释器支持集，「强度不能被实施」。
- **I9 · 协议骨架独立于 session 的边界**：session 图 = 用户知识体系（面向人）；协议信封 = agent 通信（面向 agent）。二者数据类型不同、生命周期不同、消费者不同，不该复用同一结构（呼应学员「低效」的判断）。
