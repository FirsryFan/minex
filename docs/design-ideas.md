# Minex 设计思想继承文档

> 本文档记录 Minex 讨论中**学员（项目设计者）的原创思考与关键判断**。
> 这些判断是 Minex 架构的灵魂，后来人接手前应完整理解，不要只看代码。
> 每条含：原话精要 → 展开解释 → 落地体现。

---

## 〇、总纲：Minex 追求什么

三个贯穿始终的判断：

1. **软件本体极轻量，随处是插件接口**——知识库、对话、agent、multi-agent 全部插件化，内核不认识任何领域。
2. **先做精巧设计，让「基本功能也能插件化」，不急着实际制作**——架构正确性优先于功能堆叠。
3. **打磨好已有、用尽内核接口之后，才全面转向 agent 驱动**——稳健演进，不冒进。

---

## 一、架构哲学：内核、驱动、分层

### 1. 「驱动」命名（而非「插件」）

**原话**：插件应该叫「驱动」。因为「扩展」体现不出它功能的核心性质——没有扩展这个软件根本什么功能都没有。

**展开**：这是对「内核-驱动」关系本质的洞察。插件这个词暗示「可选附加」，但 Minex 里功能是**必需**的：没有文件系统驱动就没有文件访问，没有外观驱动就没有主题，没有 agent 驱动就没有 AI 能力。类比设备驱动——没有显卡驱动就没有显示。命名即契约：**驱动 = 让软件「运转起来」的东西，不是装饰。**

**落地**：全项目统一用 `Driver` / `driver`（`DriverManifest`、`kernel.drivers`、`packages/*-driver`）。

### 2. 内核只留机制，内容归驱动、表现归 UI

**原话**（多次强调）：内核面对的是广义的「功能」，所以这个软件结构还可以面向很多其他功能，甚至打开 PDF 或编辑 markdown。

**展开**：内核最初被过度膨胀（一度想把 stage-runner、设置渲染、UI 布局都塞进内核），被学员连续砍掉。最终收敛为四个纯机制原语（registry/events/storage/lifecycle）。判据：**内核不能假设「工作是怎么被组织的」**——一个 PDF 查看器不需要 stage，所以 stage-runner 不能进内核；设置渲染含「表现」成分，属于 UI 层。

**落地**：`@minex/kernel` 四原语，零领域概念（不出现 Tool/Stage/Conversation/Theme 字样）。

### 3. 通用软件结构是独立子项目

**原话**：第一个项目把这个通用软件结构做出来，然后第二个项目是写具体的 agent 插件。

**展开**：内核（Project 1）与 agent 能力（Project 2）分离。这保证内核真正「领域无关」，agent 只是众多驱动之一。这是「先做一个通用宿主，再在其上做任何功能」的路线。

**落地**：Minex 仓库 `packages/kernel`（通用）+ `packages/*-driver`（功能），内核 tag v0.2.x 独立演进。

### 4. 布局内核固定，插件只往槽位填内容

**原话**：一些基本的框架（左栏类顶栏类右栏类浮窗类等等）还是直接设置。过高的自由度在这种不是很重要的地方只会让软件和插件过分冗余。

**展开**：通用性不等于「所有东西都可配置」。外壳的**结构**（顶栏/左栏/右栏/主区/浮窗）由内核固定，插件的自由度体现在**内容**（往槽位填什么）。这是对「插件化」边界的精确把握——VS Code 也是这个做法。

**落地**：外壳固定布局 + `panel` 贡献（驱动往 dock 槽位填内容，defaultDock 声明位置）。

## 二、运行时模型：实体、抽象、图论（学员独立产出的核心）

### 5. 实体层 / 抽象层模型

**原话**：层次具有实体层和抽象层……实体层的逻辑结构就是全展开图……消息流、事件流是在实体层上运行的。

**展开**：这是学员**独立推导**出的运行时模型，纠正了早期「三层是三个实体」的错误认知。核心命题：
- **实体只有一个**（运行时/全展开图），三层（组织流/工作流/控制流）是**同一个实体在不同粒度下的逻辑视图**，不是三个并列的东西。
- **抽象层不是幻影，是约束**——运行时可以不认识「层」，但层的结构必须能被运行时实例化。
- **消息类型 = 抽象层结构在传输层上的投影**——A2A 消息存在是因为组织流层有多个 agent；A2T 消息存在是因为控制流层有工具。**设计消息模型时，先从架构结构推出消息类型，而不是凭空造。**

**落地**：`Agentic-架构视图模型.md` 成稿（含术语替换表：运行时层/unfolding/trace/SCC condensation 等）。

### 6. 全展开图 + 宏动作 + HTN

**原话**：把 LangGraph 的每个节点变成 LangChain 最基本操作的节点，得到一个详尽的不可再展开的 LangGraph，称为全展开图。这个全展开图才是实际运行时的流程。然后逻辑上把全展开图划分成 HTN 的逻辑框架和宏动作的子图实现。

**展开**：区分了「运行时的真实结构」（全展开图）和「人脑中的逻辑组织」（HTN 框架 + 宏动作）。宏动作（options）是**按功能划分**的概念，与结构形式无关——可以是环，也可以是任意子图。这为将来「图形画布」提供了理论基础：画布上看到的是 HTN/宏动作的**规划视图**，实际跑的是**展开图**。

**落地**：概念已沉淀（unfolding / options / HTN 术语替换），图形画布里程碑的指导思想。

### 7. LangDAG（缩点）—— 规划视图与运行视图

**原话**：把环缩成点，剩余部分变成 DAG。DAG 可以进行拓扑排序、动态规划，工程也有工期、阶段性成果……循环结束有其目标，达成目标就出循环。LangDAG 把具体的循环过程缩点，只保留循环的目的，指向性更强。

**展开**：学员独立提出「缩点」（= SCC condensation）。洞察：**DAG 是规划视图，环是运行视图**。开发者脑子里应该是缩点后的阶段图（里程碑、工期），但运行时必须把环展开（因为环内迭代次数和退出时机依赖运行时决策，预先不可知）。这是「怎么想」与「怎么跑」的分离。

**落地**：概念沉淀；对应 RL 的 options、规划的 HTN。

### 8. Agent = 自动机（组合 vs 时序）

**原话**：这指出时序在什么情形下具有意义：有环才叫状态，才叫时序，agentic 是时序的，不是组合的。组合也有先后顺序，但没有反馈。

**展开**：精确的数电映射——LCEL=组合逻辑（无记忆纯前馈 DAG），agent-loop/LangGraph=时序逻辑（寄存器+反馈）。**「时序」的核心是「后效性」（当前输出依赖历史），不是「先后顺序」。** 反馈回路（输出绕回输入）就是「环」，有环才有状态，才叫时序。这给出了判断「一个系统是否 agentic」的判据：**有没有环 + 有没有状态**。

**落地**：框架谱系判断的基石（LangChain 无环无状态=组合，LangGraph 有环有状态=时序）。

## 三、Agent 设计：ReAct、Level、无为而治

### 9. ReAct 是控制流通式

**原话**：Plan & Execute 以及其他任何 agent 运行模式都是对 ReAct 的特化，ReAct 是最高阶的抽象。P&E 将 Thinking 部分特化出一个步骤 Plan，本质还是 ReAct 模式。

**展开**：把「思考放在行动的什么位置」抽象成一条轴——单次调用（无思考）→ ReAct（行动中交错，短视）→ P&E（行动前全局+行动中局部，长视野）→ Reflection（行动后）。所有模式都是这条「思考视野轴」的参数。**本质不同的模式不在控制流轴，而在另外两轴：谁思考（多 agent）、什么记忆（记忆架构）。** 设计空间是三维的：思考时机 × 思考者个数 × 记忆结构。

**落地**：agent 驱动的设计坐标系——loop 是基板，pattern 是基板上的可选策略。

### 10. Level 2 要抛弃 P&E，让 agent 自己设计行为

**原话**：Level 2 级别的 agent，特殊之处在于能够自主处理 prompt 和设计行为模式。所以要做到 level2 就必须抛弃类似 P&E 的想法，而让 ReAct 的具体步骤由 agent 自己进行设计。架构设计师要做的是保证能完成 ReAct 循环，而具体的 thinking、action、observation 和步骤之间、主体之间的信息传递方式都要交给 agent 去调整。

**展开**：这是对 Level 2（元认知）的精确理解。**架构师的责任边界**：保证 loop 能转；**agent 的自主权**：loop 的每一步怎么做、信息怎么传递。这对应「固定 vs 可变」的正确切分——固定的是循环基板，可变的是策略。

**落地**：Minex 的 stage-runner 设计哲学（阶段列表是数据不是代码，agent 可改自己的阶段配置）。

### 11. 无为而治

**原话**：为了达到 Level2 反而需要「无为而治」——只提供 mainAgent 和 subAgent 之间的消息通道，具体的消息格式都靠他们自己。

**展开**：多 agent 交互的极简主义。精确化：**「无为」发生在内容层**（agent 决定消息里写什么、怎么结构化）；**「不可无为」发生在信封层**（寻址、任务生命周期必须有个最小约定，否则两个 agent 连怎么开始说话都不知道）。连 A2A 协议本身也只是约定信封，内容仍由 agent 自由发挥。这与「ReAct 是基板、策略归 agent」是完全一致的——**通道=基板（固定），消息格式=策略（agent 决定）。**

**落地**：未来 A2A/agent 驱动的设计原则。

### 12. HTN 是基元，可写进代码

**原话**：有些结构是基元的，而且需要 agent 一开始就依赖的，比如 ReAct。HTN 的框架是通用、普适、基元的……这就是可以写进代码的框架，给定数据流动的方式。

**展开**：区分「基元结构」（固定，写进代码）和「自主化细节」（可变，agent 决定）。基元 = 循环 + 消息通道 + hook 点；细节 = 数据流动类型、语言等。**这是「架构师写什么 vs agent 调什么」的边界。**

**落地**：内核的扩展点（registry/events）+ hook 点设计。

### 13. Level 1→2 的代码实现只需要一个「再加工步骤」

**原话**：pi agent 虽然是 Level1 因为把所有 message 直接填充，但是 Level2 的代码实现肯定类似。因为只要需要 message 的交流，就一定有对象被填充。至于被填充的内容，这才是 Level2 与 Level1 的区别所在，只需要添加一个可选的 agent 再加工步骤就行了。

**展开**：极简的 Level 升级路径洞察。Level 1 和 Level 2 的代码结构**几乎相同**（都是填充消息），唯一区别是填充**前**有没有一个「再加工」环节。这个「再加工步骤」就是 hook（挂在上文回灌路径上）。**用最小的架构改动支持最大的能力跃迁。**

**落地**：context engineering 的 hook 设计 = 再加工步骤。

### 14. subagent 当 tool 的质疑

**原话**：multi-agent 时如果仅仅把 subagent 当作 tool 进行消息传递我认为不太合理。

**展开**：指出「工具 = 另一个 agent」这一框架观点的局限。函数调用是「请求-响应」一次成型，**丢掉了 agent 的会话性（多轮）、状态、目标**。真实的 agent↔agent 交互是 A2A（任务生命周期、多轮消息、工件传递），不是函数调用。这是对「统一契约」思想的必要修正——统一不能抹杀本质差异。

**落地**：未来 A2A 章节的设计依据（Ch15）。

## 四、交互与产品设计

### 15. 主题本质是扩展

**原话**：主题本质上还是扩展，只不过因为功能特殊命名为「主题」。但是我们需要把扩展系统的标签做好。

**展开**：打破「主题 vs 扩展」的二元。主题是扩展的一种（kind），只是语义特殊。**统一的扩展系统 + 标签（tags/kind）** 是市场筛选、管理的基础。

**落地**：`DriverManifest.tags` / `kind` 字段；appearance 的主题管理 UI 复用扩展概念。

### 16. markdown 编辑器本质是渲染器

**原话**：markdown 编辑器的本质就是普通记事本 + markdown 渲染，不如把编辑器改成渲染器，这样更加高效。任何地方等效于让该驱动获得被渲染的朴素文本然后给出渲染结果。这样可以设计聊天视图，用于保存和渲染 agent 的对话文件。

**展开**：**抽象层级的提升**。编辑器（编辑/预览/分屏/即时四模式）只是「渲染器」的四个消费者。渲染器的核心契约是 `文本 + 选项 → HTML`，是纯函数。这样聊天视图、对话文件渲染、README 显示全部复用同一个能力，而非各自实现。

**落地**：`markdown.render` 通用能力（被 appearance 消费渲染 README）；renderMarkdown 纯函数（highlight.js + KaTeX + 换行配置）。

### 17. 文件系统是独立驱动 + 安全边界

**原话**：文件系统做成独立驱动，后续 markdown 文件的存储访问、agent 工作文件仓库等等都要靠它。这一步要保证安全性，所有文件都要放在指定的文件夹里面。

**展开**：文件系统是**基础驱动**（其他驱动依赖它），不是某个驱动的附属。安全是第一原则：**所有路径限制在用户选定的根目录内**（拒绝绝对路径、拒绝 `..` 逃逸）。这是「能力可以被复用，但不能越界」的体现。

**落地**：`filesystem-driver` 的 `path.ts`（resolveSafePath 纯函数 + 测试）；`FileSystemAbility` 接口（浏览器 File System Access API 实现，Node/Electron 接口一致可替换）。

### 18. 驱动默认占侧边栏（依赖驱动也显示）

**原话**：文件资源驱动默认占用一个侧边栏。虽然顶栏左侧可以选择哪个驱动作为主体显示于整个界面，有些驱动也要依赖于别的驱动，这时别的驱动也应该在区域内有所显示。

**展开**：**「活动驱动」与「依赖驱动」的共现**。主体显示活动驱动，但基础驱动（如文件系统）应该常驻侧边栏，因为其他驱动依赖它。这打破了「选中一个驱动就独占整个界面」的简单模型，支持了「文件树常驻 + 活动驱动主体」的布局。

**落地**：外壳三段布局（侧边栏/主体/右栏各自可被驱动贡献替换）+ `panel` 贡献（defaultDock 声明位置）。

### 19. 暂存式启用/禁用（学员提出的方案）

**原话**：选择完禁用之后并不会立刻禁用或者启用，而是要点击重新加载，此时会对所有发生变化的项目进行重新加载。

**展开**：把「变更」和「生效」分离。点按钮只标记待变更（pending），点「重新加载」统一应用。这避免了「即改即生效」的状态竞态，也与「驱动变更需重载生效」的语义一致。禁用被依赖的驱动要弹警告。

**落地**：驱动管理的 `planApply` 纯函数（依赖拓扑排序 + 冲突检测）+ pending 状态 + 确认弹窗。

### 20. 背景色是「层级」，不是「位置」

**原话**：背景色是所有底色……左栏右栏，也是文字显示在背景之上的。这些地方都叫背景，背景是和文字、图标区分的一个层级，而不是某个具体的位置。

**展开**：**语义层级 vs 空间位置的区分**。背景不是「某个叫 background 的地方」，而是「文字/图标之下的一层底色」——顶栏、左栏、右栏、主体全是背景层。这纠正了「背景色只影响某个区域」的错误实现。

**落地**：`--color-bg`（背景层，所有底色）vs `--color-card`（表面层）的分层；backgroundColor 设置派生 card/hover（color-mix）。

### 21. 主题色的交互语义（中性底 + 悬停显现）

**原话**：大部分按钮保持黑底白字白底黑字，但是指针浮在上面会显现出主题色表示选中。被选中内容可以用主题色框线框出来的方式，仍然保持白底黑字黑底白字。

**展开**：主题色不该「涂满」所有交互元素，否则喧宾夺主。正确用法：**默认中性（黑白），悬停显现主题色（表示可交互），选中用主题色框线（表示状态）**。这让主题色成为「强调」而非「底色」。

**落地**：`.btn` 中性底 + hover 主题色；active 态 inset 框线。

### 22. 自动保存 + 手动重载的语义

**原话**：任何切换画面都应该保持原有的设置是一个被保存状态……这个时候是随时保存但是并没有重新加载。此时应该在对应栏目的右边显示「未完成」的颜色。

**展开**：区分「保存」（持久化，随时做）和「重载」（生效，手动触发）。切换画面不丢状态（自动保存到 storage），但生效要等重新加载。未生效的变更用「未完成」黄色标记（可配置颜色），且**逐级定位到精确位置，所有父级目录都打上颜色标记**。

**落地**：设置自动保存（debounce 写 storage）+ 手动重载语义 + `--color-warning`（未完成标记色，可配）。

### 23. 字体全局一致 + 表单元素也继承

**原话**：字体仅仅不在选择字体的地方渲染。其他条目，比如「图标体系」里的「简约/默认」这里的字体是没有收到调整的。显然应该与全局字体一致。

**展开**：全局字体设置要**覆盖所有 UI 文字**，包括下拉选项、表单元素（它们默认不继承 body 字体）。这是「设置真正生效」的完整性要求——不能只改某几处。

**落地**：`input/select/textarea/button { font-family: inherit }` + `--font-ui` 全局令牌。

### 24. 调色板要可拖动

**原话**：还是要调色板，但是要可以拖动选中的东西。调色盘这样子是在考验精度吗，像素级瞄准？

**展开**：颜色选择应该是**连续拖动**（HSV 色相条 + 饱和度/亮度二维平面），不是系统取色器「点一下弹窗、像素级瞄准」。交互要顺滑、可拖、实时预览。

**落地**：自研 HSV 调色板（色相条 + SV 平面，可拖动，hex↔hsv 纯函数 + 测试）。

### 25. 简洁大气，删冗余说明

**原话**：不要在软件里写上冗余的说明用途的文字……请统统删除。卡片/按钮一定要有反馈机制，鼠标指针落在上面可以轻微向上弹跳或者让它变亮一点。

**展开**：产品文案的克制 + 交互反馈的必要。说明文字是噪音（功能自己会说话）；hover 反馈（上弹/变亮）是交互的「手感」，必须有。

**落地**：删除「（空槽位）」「预览 Preview」等；hover 上弹 translateY + 变亮 transition。

## 五、学习与工作方法论（影响协作方式）

### 26. 渗透学习法

**原话**：内容知识上不封顶、无完整学习体系 → 不穷尽单个仓库。带着「已学的核心概念」去其他 agent 平台看相同内容的实现。

**展开**：拒绝线性穷尽。用「主题透镜」（主循环/消息模型/工具回灌/钩子/事件流式/上下文/会话）横向对比各仓库的同一主题，而非从头读。

**落地**：仓库路线 Pi → OpenHands → Hermes → Letta → Cherry Studio。

### 27. 三轨协同

**原话**：书=概念坐标 / 仓库=参考答案 / 项目=考题。三轨永远同一主题。

**展开**：学习闭环。书给命名和坐标系，仓库给实现参考，项目是检验理解的地方。三轨必须在同一主题上同步推进，不能各学各的。

**落地**：读书（Agentic Design Patterns）+ 看仓库 + 做项目（Minex）同步。

### 28. 建设模式切换

**原话**：时间有限，先搭建起个人 agent 平台达到可用效果，文化课提升后再回来阅读更前沿具体的部分做优化。

**展开**：目标驱动的优先级管理。知识储备超过产出时，果断切到「建设模式」（项目轨 80%，读书降为建时查阅），等基础满足后再回到「优化模式」。**不建，理解力就浪费了。**

**落地**：三轨配比的动态调整。

### 29. 第一性原理最重要（工科 vs 数学）

**原话**：数学不管思路来源只问正确性，思路来源不重要。工科常常没有唯一固定答案，所以才有「优化」问题，这也导致了第一性原理最重要。

**展开**：对「如何做对一件事」的学科洞察。数学接受任何证明（只看对错），工科目标函数多（成本/延迟/可维护性/正确性）、约束是硬事实——所以**从约束推导可行域**（第一性原理）比联想猜答案更可靠。

**落地**：设计时先列硬约束（上下文窗口有限、输出概率、调用有成本、会幻觉），从约束推导设计。

### 30. 纯逻辑抽纯函数 + 自动化测试

**原话**（配合审查经验形成）：纯逻辑必须抽纯函数，UI 组件层不承载可测逻辑。

**展开**：这是从「反复被抓『表面正常、特定输入静默失效』类 bug」中总结的工程纪律。CSS 生成、计划排序、路径校验等可计算逻辑必须从 UI 抽出为纯函数并测试，否则「改了看不出错」的 bug 永远漏检。

**落地**：`planApply`/`buildCss`/`resolveSafePath`/`applyFormat` 等都是纯函数 + 测试；typecheck 是提交硬门槛。
